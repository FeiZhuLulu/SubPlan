# 满意度优先的订阅推荐算法设计

日期：2026-08-01

状态：待用户书面审阅

适用项目：SubPlan

## 1. 背景

2026-07 数据更新后，启用推荐的方案从 43 个增加到 64 个，模型、套餐、额度和地区价格更丰富，但现有算法仍以套餐级静态能力分、单一月度 MTokens 额度、贪心分配和固定组合加减分为主。离线审计发现以下问题：

- 地区、支付和附加需求的部分输入未真正参与排序。
- 相同品牌的互斥订阅档位可能同时出现。
- 固定互补加分和预算利用率加分会让更贵、核心效用更低的组合排在前面。
- API 方案会自动花完剩余预算。
- 额度置信度、周窗口和模型级信息没有充分参与计算。
- 每次推荐反复读取 JSON，数据规模增大后单次调用明显变慢。

本设计将推荐目标从“静态总分最高”改为“购买并实际使用后最可能满意”，同时保持算法可解释、可校准，并适应当前真实用户反馈较少的阶段。

## 2. 已确认的产品决策

1. 第一目标是用户购买和使用后的真实满意度，而不是点击率或预算消耗率。
2. 采用规则、公开数据和专家体验结合的可解释算法，不在当前阶段训练黑盒 Learning-to-Rank 模型。
3. 网页版不作为独立使用入口或独立需求池，只能提供有上限的套餐价值加成。
4. 响应速度不进入主排序，只在结果页作为附加标签或说明。
5. Claude 对 CN 用户不做硬性排除，只降低展示优先级。
6. 暂不考虑外币卡。GLOBAL 套餐可推荐给 CN 用户；没有 CN 价格时使用官网美元价并换算成人民币。
7. 前端能力主要参考 Arena；Agent 编程和后端能力使用公开评测与专家体验共同校准。
8. 已确认的 Agent/后端专家排序锚点为：

   `GPT-5.6 Sol > Kimi K3 > GPT-5.5 ≳ Grok 4.5 > GLM 5.2 > Kimi 2.7 Code`

9. Opus 5 与 Opus 4.8 独立评估，不因为版本号更新就默认前者更强。
10. GPT Plus 网页版在常规高强度使用中极少触顶，应获得有限加成；GPT Pro 5x/20x 因网页版提供 GPT-5.6 Pro，在高难度需求中获得额外加成。

## 3. 目标与非目标

### 3.1 目标

- 首选组合满足用户的主要任务、总用量和高智能需求。
- 预算被视为上限，不鼓励为了接近预算而增加无价值支出。
- 在效用相近时优先选择更便宜、更简单、证据更可靠的组合。
- 不把不可同时购买的订阅档位组合在一起。
- 将地区体验、数据置信度和额度风险显式呈现。
- 推荐原因能够追溯到真实的任务分配、额度贡献和套餐加成。
- 数据继续增长时保持可接受的服务端响应时间。

### 3.2 非目标

- 不根据点击率自动训练个性化模型。
- 不采集提示词、聊天正文、银行卡或其他敏感信息。
- 不把响应速度转换为主排序分数。
- 不为网页端单独要求用户填写用量。
- 不在本阶段精确判断每一种支付渠道是否可用。
- 不承诺社区额度估算等同于官方硬上限。
- 不在本次算法升级中实现用户反馈采集页面或线上实验平台；本次只预留版本字段和反馈数据契约。

## 4. 概念模型

算法拆分为四层，每层只负责一种决策。

### 4.1 硬约束层

负责方案是否能够进入候选集合：

- 套餐必须启用推荐。
- 免费主订阅不能作为新的付费推荐，但可作为已有方案参与计算。
- API 仅在用户接受 API 计费时进入候选集合。
- 固定套餐总价不能超过预算容忍范围。
- 同一互斥订阅组最多选择一个主订阅档位。
- 已有订阅升级时，用新档位替换旧档位，并单独计算升级增量。

### 4.2 任务满足层

负责把用户需求分配给组合中的模型和额度：

- 需求由能力维度、总用量和高智能比例组成。
- 每个套餐提供一个或多个模型能力，以及一个或多个共享额度池。
- 普通需求和高智能需求共同消耗物理额度。
- 使用全局优化而不是按能力逐项贪心，避免优质额度被过早消耗在可由其他套餐承担的任务上。

### 4.3 套餐价值层

负责不适合直接转换成 MTokens 的产品价值：

- 网页版高可用额度加成。
- 极高难度任务可用的额外高端模型加成。
- 地区展示优先级。
- 数据置信度和额度风险。
- 响应速度标签，仅用于解释。

### 4.4 最终排序层

负责从可行组合中选出最值得展示的结果：

- 先删除被其他组合支配的结果。
- 再按稳健满意度排序。
- 满意度接近时，依次优先更便宜、套餐更少、证据更可靠的组合。
- CN 地区的 Claude 组合默认进入降级展示层，但在没有其他可行方案时仍可展示。

## 5. 数据结构设计

### 5.1 互斥订阅组

在 `plans.json` 的每个主订阅中增加可选字段：

```ts
exclusiveGroup?: string;
```

同一 `exclusiveGroup` 的主订阅不能同时出现在一个组合中。示例：

- `chatgpt_membership`：ChatGPT Plus、Pro 5x、Pro 20x。
- `kimi_membership`：Kimi 各会员档位及其区域镜像。
- `google_ai_membership`：Google AI Plus、Pro、Ultra。
- `supergrok_membership`：SuperGrok Lite、SuperGrok、Heavy。

API 不与同品牌主订阅互斥，因为它们是可独立购买的补充计费方式。

### 5.2 额度池

模型访问画像增加明确的额度池和模型消耗倍率：

```ts
type QuotaPool = {
  quotaPoolId: string;
  capacityMTokens: number;
  confidence: "high" | "medium" | "low";
  source: string;
};

type ModelAccessModel = {
  modelId: string;
  label: string;
  quotaPoolId: string;
  workloadMultiplier?: number;
  tierByCapability: Partial<Record<CapabilityKey, IntelligenceTier>>;
};

type ModelAccessProfile = {
  planId: string;
  quotaPools: QuotaPool[];
  models: ModelAccessModel[];
  notes?: string;
};
```

规则：

- 共享同一钱包或限额的模型必须使用同一个 `quotaPoolId`。
- `capacityMTokens` 是额度池的唯一物理容量，不能因为池内包含多个模型而重复累加。
- `workloadMultiplier` 表示相对于额度池基准模型的工作负载倍率；缺省为 1。分配 `x` MTokens 工作负载时消耗 `x / workloadMultiplier` 个池容量单位。
- 缺少额度池信息的旧数据迁移为一个 `${planId}:default` 池，其容量取 `quotas.json` 的套餐级额度。
- 旧模型记录中的 `quotaMTokens` 和 `quotaShare` 只用于迁移脚本推导额度池，不再由运行时直接相加。
- Cursor 等存在高级模型池和普通模型池的套餐应建立多个池；Claude、Kimi 等共享钱包中的多个模型必须指向同一池。

### 5.3 推荐策略配置

新增 `data/recommendation-policy.json`，存放产品策略，不把策略散落在 TypeScript 常量中：

```ts
type RecommendationPolicy = {
  schemaVersion: string;
  confidenceFactors: {
    score: Record<"high" | "medium" | "low", number>;
    quota: Record<"high" | "medium" | "low", number>;
  };
  webValueSignals: Array<{
    planId: string;
    baseBonus: number;
    extremeTaskBonus?: number;
    label: string;
    confidence: "high" | "medium" | "low";
    evidence: string;
  }>;
  regionPresentationRules: Array<{
    region: "CN" | "US" | "JP" | "GLOBAL";
    provider?: string;
    planId?: string;
    tier: "normal" | "deprioritized";
    explanation: string;
  }>;
  speedLabels: Array<{
    planId?: string;
    modelId?: string;
    label: string;
    evidence: string;
  }>;
};
```

首批策略值：

- ChatGPT Plus：`baseBonus = 2.0`，说明网页版额度在常规高强度使用中极少触顶。
- ChatGPT Pro 5x/20x：`baseBonus = 2.0`；当高智能档位为 `high` 或 `extreme` 时再加 `extremeTaskBonus = 1.5`，反映 GPT-5.6 Pro 网页访问价值。
- 单个组合的网页价值加成上限为 3.5 分。
- CN + Anthropic：展示层级为 `deprioritized`。
- Grok 4.5 可配置“响应较快”标签，但该标签不改变最终分数。

### 5.4 专家校准记录

新增 `data/model-calibration.json`，保存专家排序锚点和证据，不直接保存最终套餐名次：

```ts
type ModelCalibration = {
  capability: CapabilityKey;
  orderedModelIds: string[];
  evidenceType: "expert_experience" | "community_consensus";
  confidence: "high" | "medium" | "low";
  notes: string;
};
```

校准脚本使用排序约束检查模型分数：相邻模型允许小幅接近，但不得出现与高置信度锚点明显相反的结果。专家锚点用于发现和复核异常，不在运行时强行覆盖所有 Benchmark。

### 5.5 首批真实体验证据

- GPT Plus 网页版在实际高频使用中几乎未触顶，仅用于支持 `webValueBonus`，不转换成 MTokens。
- GPT Plus 的 Codex 额度继续以版本化统计数据为主；“GPT-5.6 Sol Max 可连续运行数小时重任务”作为合理性复核信号。
- Kimi 199 / K3-256k 的本地 `ccusage` 观测为每周约 2.94 亿 workload tokens，缓存命中率约 98.2%。按年周数折算约 12.7 亿 workload tokens/月；该记录作为高可信社区观测与现有额度交叉校验，不能把缓存 token 直接解释为同等的新生成 token。
- Grok 额度完全使用版本化数据库数据，不使用个人半日消耗比例估算；“响应较快”只保留为结果标签证据。

## 6. 地区与价格规则

### 6.1 候选地区

- CN 用户：允许 `CN` 和 `GLOBAL` 套餐。
- US 用户：允许 `US` 和 `GLOBAL` 套餐。
- JP 用户：允许 `JP` 和 `GLOBAL` 套餐。
- GLOBAL 用户：只允许 `GLOBAL` 套餐，避免混入 CN、US 或 JP 专属方案。

### 6.2 价格选择

1. 固定订阅优先使用用户地区的可信月付价格。
2. US/JP 有已映射的 App Store 月付价格时使用该价格，并保留来源说明。
3. 没有本地价格时使用套餐官网原币月价。
4. 最终统一按 `fx-rates.json` 换算成人民币，同时保留原币价格用于展示。
5. CN 用户购买 GLOBAL 美元套餐时不做外币卡过滤或降权。
6. API 使用其实际计价币种换算，不使用固定月价。

## 7. 能力与高智能模型校准

### 7.1 能力分

原始能力分继续使用 0–100 标尺，但加入置信度收缩：

```text
稳健能力分 = 50 + (原始能力分 - 50) × 置信度系数
```

系数：

- high：1.00
- medium：0.95
- low：0.85

这样不会让低置信度的高估分数直接成为首选，同时不会完全抹除新模型的潜力。

### 7.2 高智能适配系数

用户选择的高智能比例只决定高智能需求量；模型档位决定每单位物理额度可折算出的高智能有效工作量。

| 用户档位 | S | A | B | C | D |
| --- | ---: | ---: | ---: | ---: | ---: |
| low | 1.00 | 1.00 | 0.70 | 0.30 | 0.00 |
| medium | 1.00 | 0.75 | 0.25 | 0.00 | 0.00 |
| high | 1.00 | 0.40 | 0.00 | 0.00 | 0.00 |
| extreme | 1.00 | 0.15 | 0.00 | 0.00 | 0.00 |

所有套餐都使用同一张表。没有模型画像时使用套餐的 `model-tier`，不再使用另一套 fallback 系数。

适配系数只应用一次：若模型的工作负载倍率为 `m`、高智能适配系数为 `f`，则额度池的每个物理容量单位最多产生 `m × f` 个高智能有效工作量单位。分配 `x` 个高智能有效 MTokens 时消耗 `x / (m × f)` 个池容量单位；普通需求消耗 `x / m`。能力质量分不再重复乘以 `f`。

### 7.3 专家排序锚点

Agent 编程和后端能力数据更新后必须满足以下复核约束：

- GPT-5.6 Sol 不应低于 Kimi K3。
- Kimi K3 不应低于 GPT-5.5。
- GPT-5.5 与 Grok 4.5 可以接近，但 Grok 4.5 不应在缺少新证据时明显反超。
- GLM 5.2 不应高于 Grok 4.5。
- Kimi 2.7 Code 不应高于 GLM 5.2。
- Opus 5 与 Opus 4.8 独立评分，允许 4.8 在部分能力上更高。
- 前端能力优先服从同一评测口径的 Arena 数据。

“明显反超”定义为相差超过 3 分。出现反向差距时数据校验报告必须列出证据，人工确认后才能接受。

## 8. 需求与额度分配

### 8.1 需求构建

- 主用途贡献 70% 初始权重。
- 有效次用途贡献 30% 初始权重。
- 附加能力按配置增加权重后统一归一化。
- `mobileExperience` 和 `ideIntegration` 不再伪装成能力 token：
  - `mobileExperience` 转换为套餐特性偏好，检查 `mobile_app`。
  - `ideIntegration` 转换为套餐特性偏好，检查 `ide` 或 `ide_plugin`。
- 这两个特性只在满足主要任务的候选之间做最多 1.0 分的偏好调整，不能替代任务能力。

### 8.2 全局分配优化

对每个候选组合建立小规模最大效用流问题：

- 需求节点：每个能力的普通需求和高智能需求。
- 供给节点：组合中的额度池与可访问模型。
- 边容量：额度池剩余物理容量，以及高智能适配换算后的有效容量。
- 边价值：稳健能力分。

采用词典序目标：

1. 最大化高智能需求覆盖量。
2. 最大化总需求覆盖量。
3. 在覆盖量相同的情况下最大化分配质量。

组合最多三个新增方案，因此可以使用确定性的最小费用最大流或等价线性优化，不依赖近似贪心结果。

`qualityScore` 的分母始终是用户总需求；未分配需求按 0 分计入。这样覆盖不足的组合不会因为只服务了少量高分任务而获得虚高质量分。

### 8.3 额度置信度

稳健额度用于风险评分和硬门槛：

```text
稳健额度 = 估算额度 × 额度置信度系数
```

系数：

- high：1.00
- medium：0.90
- low：0.75
- not_applicable：API 动态计算，不做固定额度收缩。

界面仍展示原始估算额度，并明确说明稳健额度只用于推荐排序。

### 8.4 覆盖门槛与余量

- 正常可行组合：稳健总覆盖率至少 90%，稳健高智能覆盖率至少 90%。
- 满意覆盖目标：总覆盖率至少 110%，高智能覆盖率至少 100%。
- 超过 125% 的总覆盖和超过 110% 的高智能覆盖不继续增加满意度，防止超大额度无上限抬高排名。
- 没有正常可行组合时返回最接近门槛的结果，标记为“预算或额度不足”，而不是返回空列表。

## 9. API 动态预算

### 9.1 价格字段归一化

导入层统一接受以下别名：

- `inputCacheMiss` 或 `input`
- `inputCacheHit` 或 `cacheHit`
- `output`

启用 API 的三个价格字段必须为有限非负数。缺失字段的方案不进入候选集合，并在数据校验报告中报错，不能让 `NaN` 静默流入推荐。

### 9.2 实际花费

API 预算是连续决策变量，而不是自动等于剩余预算：

- API 最低花费为 0。
- API 最高花费为固定套餐后的剩余预算。
- 只购买补足需求和目标安全余量所需的额度。
- 不购买超过 125% 总覆盖上限所需的 API 额度。
- 多个 API 同时存在时，按高智能适配、能力和每元有效额度进行联合分配，不做平均分账。
- 组合价格等于固定费用加实际 API 花费。

## 10. 满意度与排序

### 10.1 基础指标

每个组合计算：

- `qualityScore`：全局分配后的稳健能力质量，0–100。
- `robustTotalCoverage`：稳健总覆盖率。
- `robustHighCoverage`：稳健高智能覆盖率。
- `coverageReliabilityScore`：覆盖余量和额度置信度形成的 0–100 分。
- `webValueBonus`：0–3.5。
- `featurePreferenceBonus`：移动端和 IDE 偏好形成的 0–1.0。

覆盖可靠性分采用分段线性规则：

- 任一稳健覆盖低于 90%：低于正常可行层，不参与正常首选。
- 总覆盖 90% 对应 75 分，110% 对应 100 分。
- 高智能覆盖 90% 对应 75 分，100% 对应 100 分。
- 两者按 40% 总覆盖、60% 高智能覆盖合成。

### 10.2 稳健满意度

```text
稳健满意度 =
  qualityScore × 0.78
  + coverageReliabilityScore × 0.22
  + webValueBonus
  + featurePreferenceBonus
```

分数不额外奖励预算利用率，也不添加通用的“聊天订阅 + 编程订阅”固定互补分。互补价值必须通过实际分配质量或覆盖提升体现。

### 10.3 组合有效贡献

新增套餐必须满足至少一个条件：

- 承担不少于总需求 12% 的有效分配；或
- 将稳健高智能覆盖提高至少 10 个百分点；或
- 将 `qualityScore` 提高至少 1.5 分。

API 补位可使用更低门槛：承担至少 5 MTokens 且不少于总需求 5%，但实际花费必须由需求缺口决定。

### 10.4 Pareto 过滤

若组合 A 同时满足以下条件，则组合 B 被 A 支配并从主结果移除：

- A 的实际价格不高于 B。
- A 的稳健满意度不低于 B，包括网页价值和特性偏好。
- A 的稳健总覆盖不低于 B，比较时覆盖上限截断为 125%。
- A 的稳健高智能覆盖不低于 B，比较时覆盖上限截断为 110%。
- 上述条件至少一项严格更优。

Pareto 过滤分别在 `normal` 和 `deprioritized` 展示层内执行，降级展示方案不能删除正常展示方案。被支配组合不进入主推荐和特色推荐，可以仅在调试信息中保留。

### 10.5 最终排序键

在每个“可行状态 + 地区展示层级”分组中，先计算该组最高稳健满意度，再定义：

```text
满意度分段 = floor((组内最高满意度 - 当前满意度) / 2)
```

排序依次使用：

1. 是否达到正常可行门槛。
2. 地区展示层级，`normal` 优先于 `deprioritized`。
3. 满意度分段升序；与组内最高分相差不足 2 分的方案处于同一段。
4. 同一满意度分段内，实际价格较低者优先。
5. 套餐数量较少者优先。
6. 稳健满意度降序。
7. 数据置信度较高者优先。
8. 规范化组合 ID，保证完全确定的稳定顺序。

若正常层没有任何可行组合，允许 `deprioritized` 方案或覆盖不足方案进入首选，但必须显示明确提示。

## 11. 结果解释

推荐原因必须来自计算结果，不使用泛化模板作为主要理由：

- 哪个套餐承担了哪个主要任务。
- 哪个模型承担了高智能需求。
- 稳健总覆盖和高智能覆盖。
- 新增套餐相对最佳子组合带来的边际收益。
- GPT 网页版加成或 GPT Pro 高难度加成。
- 额度置信度较低时的风险提示。
- CN 地区 Claude 降级展示原因。
- 美元或日元价格的原币金额、汇率和人民币估算。
- 响应速度标签只能作为附加说明。

结果分类从 Pareto 前沿中选择，且不同分类不能重复同一组合：

- 最推荐：最高稳健满意度。
- 省钱够用：满足正常门槛的最低成本优质方案。
- 高智能优先：高智能质量和覆盖最强。
- 额度充足：稳健总覆盖最高，但超出上限不额外得分。
- 其他可选：包含地区降级展示方案，例如 CN 的 Claude 组合。

## 12. 组件边界

将当前大型评分文件拆分为以下模块：

- `lib/recommendation/data-snapshot.ts`：一次加载、校验并索引数据。
- `lib/recommendation/eligibility.ts`：地区、角色、互斥组和已有订阅规则。
- `lib/recommendation/pricing.ts`：固定价格、地区价格和 API 成本。
- `lib/recommendation/demand.ts`：需求权重和特性偏好。
- `lib/recommendation/allocation.ts`：全局额度与能力分配。
- `lib/recommendation/ranking.ts`：稳健指标、Pareto 过滤和排序。
- `lib/recommendation/explanations.ts`：推荐理由、标签和警告。
- `lib/recommendation/validation.ts`：数据不变量与诊断报告。
- `lib/recommend.ts`：保持现有公开入口，编排上述模块。

数据快照在服务端按文件修改时间缓存；单次推荐中每个数据文件最多读取和解析一次。索引至少包括：

- `planById`
- `scoreByPlanId`
- `quotaByPlanId`
- `tierByPlanId`
- `accessProfileByPlanId`
- `relationsByPair`
- `regionalPriceByPlanAndRegion`
- `policyByPlanAndRegion`

## 13. 错误处理

- 启用套餐缺少能力分、固定额度或模型档位时，数据校验失败并指出计划 ID。
- 缺少网页价值或速度标签时按 0 加成处理，不报错。
- API 价格字段无效时排除该 API，并记录结构化诊断。
- 地区价格缺失时回退官网原币价格；官网价格也缺失时排除固定套餐。
- 额度或评分出现 `NaN`、无穷值或越界值时立即拒绝该记录。
- 没有正常可行组合时返回覆盖最接近的三个方案，并说明缺少的预算、总额度或高智能额度。

## 14. 验证与回归

### 14.1 数据不变量

- 所有计划 ID、评分 ID、额度 ID、档位 ID 和画像 ID 唯一。
- 所有启用固定套餐具有评分、额度和档位。
- 所有启用 API 具有可计算的有限价格。
- 所有模型额度池容量不重复累计。
- 所有互斥组引用存在的计划。
- 评分在 0–100，额度和价格非负。

### 14.2 算法性质测试

- CN 可以推荐 GLOBAL 美元套餐，且价格按汇率换算。
- GLOBAL 不出现 CN、US 或 JP 专属套餐。
- 同一互斥组最多出现一个主订阅。
- `mobileExperience` 和 `ideIntegration` 会改变对应特性偏好结果。
- 提高预算不能降低可获得的最佳稳健满意度。
- 关闭 API 后不出现 API；开启 API 后也不会自动花完预算。
- 主推荐中不存在被支配组合。
- 低置信度额度在硬门槛中按收缩值计算。
- 网页版加成不能让额度不足组合越过硬门槛。
- 速度标签改变说明但不改变排序分数。
- CN 有正常可行的非 Claude 组合时，Claude 不占据首选。
- 无正常可行组合时仍返回带警告的替代结果。

### 14.3 黄金场景

建立至少 30 个版本化场景，首批必须覆盖：

- CN、Agent 编程、中等预算：GPT Plus 和 Kimi 199 应处于有竞争力的前列。
- CN、极高难度且预算充足：GPT Pro 因 GPT-5.6 Pro 加成进入高优先级候选。
- 前端为主：排名方向与同口径 Arena 数据一致。
- 研究写作：不能因为编程额度大而错误主导结果。
- 高用量低预算：展示最接近门槛的方案和缺口，不返回空白。
- 已有低档订阅：推荐升级而不是叠加同品牌档位。
- API 补位：只支付补足缺口的实际成本。

黄金场景允许多个可接受答案，不要求固定唯一组合；测试以禁止项、候选集合和允许的排名区间表达。

### 14.4 性能目标

- 服务端热调用本地 p95 小于 250ms。
- 单次推荐中每个 JSON 文件最多读取和解析一次。
- 典型 64 个启用方案下，完整场景矩阵可在 CI 可接受时间内完成。
- 排序完全确定，相同输入和数据版本产生相同结果。

## 15. 反馈闭环

第一阶段只收集匿名结构化反馈：

- 输入参数、完整曝光结果、算法版本和数据版本。
- 用户最终选择的组合或未选择原因。
- 地区不可用、太贵、额度不足、功能重复、工作流不匹配等结构化原因。
- 使用 7–30 天后的额度触顶频率、满意度和是否续订。

反馈先用于更新黄金场景、置信度和校准记录。样本不足 1000 条可靠结果前，不直接训练自动排序模型。

上述反馈字段是后续版本的数据契约。本次算法升级仅在推荐响应中提供算法版本、数据版本和稳定组合 ID，不实现线上采集与回访界面。

## 16. 迁移兼容性

- 保持 `recommend(input): ScoredCombo[]` 的公开接口。
- 保留现有输入字段，`hasForeignCard` 暂时接收但不参与算法，后续可在 UI 清理。
- 现有结果页继续读取 `capabilityScore`、`finalScore`、`reasons` 和 `cautions`；新增稳健覆盖和数据置信度字段采用可选字段迁移。
- 先生成兼容数据，再切换推荐引擎；切换时使用黄金场景对照旧算法和新算法。

## 17. 验收标准

满足以下条件后视为算法升级完成：

1. 所有数据不变量和算法性质测试通过。
2. 30 个以上黄金场景通过人工审阅。
3. 主推荐中没有相同互斥组叠加或 Pareto 被支配组合。
4. API 不再出现 `NaN`，也不会无条件花完预算。
5. CN、GLOBAL、US、JP 地区规则符合本设计。
6. GPT 网页版和 GPT Pro 加成按配置生效，但不绕过额度硬门槛。
7. Claude 在 CN 降级展示但未被硬性删除。
8. 热调用 p95 小于 250ms。
9. 推荐理由能够说明主要任务、额度、高智能模型、价格和风险。
10. 现有页面和 API 接口保持兼容。
